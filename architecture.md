# Shadowfax Architecture

## Overview

Shadowfax is a lightweight security monitoring platform designed to analyse
events generated by humans, AI agents and service accounts.

This document is the source of truth for the project architecture. Where this
document and the code disagree, one of them is wrong and should be corrected
deliberately rather than left to drift.

The project is a Python backend at the repository root and a React dashboard
under `frontend/`.

```
                        Browser
                           │
                           ▼
              ┌─────────────────────────┐
              │   Dashboard (React)     │
              │   polls every 5s        │
              └────────────┬────────────┘
                           │ HTTP, JSON
                           ▼
              ┌─────────────────────────┐
              │     Shadowfax API       │   orchestrates every request
              └────────────┬────────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
       ┌──────────────┐         ┌────────────────┐
       │    SQLite    │────────►│   Detectors    │
       │              │ history │                │
       │  events      │         │  pure function │
       │  alerts      │◄────────│  of (events,   │
       │  policy      │ alerts  │   policy)      │
       └──────────────┘         └────────────────┘
```

The API is the orchestrator. Nothing else coordinates work: the detection
engine never reaches into the database, the database never invokes the
detection engine, and the dashboard never touches either.

## Design Principles

These are the invariants the rest of the system depends on. Changing any of
them is a redesign, not a refactor.

### Alerts are recomputed, never patched

Alerts for an actor are deleted and rebuilt from scratch whenever new events
arrive for that actor, or whenever the policy changes. Nothing is
incrementally updated.

This trades a little CPU for correctness and restart-safety. There is no
in-memory sliding-window state to reconstruct after a crash, and no
possibility of stale alerts surviving a policy change.

### Detectors are pure functions

`detectors.run_for_actor` is a pure function of `(that actor's ordered event
history, current policy)`. It performs no I/O, holds no state between calls
and has no side effects.

This is what makes the recompute strategy safe. Any detector that needs to
persist state between runs breaks the invariant above.

### Observability, not enforcement

Shadowfax analyses activity and produces alerts. It never blocks, modifies or
rejects an event. It is not a security boundary and must not be positioned as
one.

### Detection is deterministic and policy-driven

All detection logic is explicit rules evaluated against a policy document.
Large language models may be used to explain, correlate and summarise
activity. They are never part of the detection decision.

### The dashboard talks only to the API

No client accesses SQLite directly. Every read and write goes through a REST
endpoint, and `frontend/src/api.js` is the only file in the dashboard that
calls `fetch`.

### The dashboard holds no detection logic

The frontend decides how an alert looks, never whether it exists. Severity
colours and sort order in `constants.js` are presentation only. Any rule that
determines whether something is worth alerting on belongs in `detectors.py`,
where it is testable and where the policy governs it.

### Filtering happens server-side

The dashboard sends filter state to `/alerts` as query parameters rather than
fetching everything and filtering in the browser. The API already supports
this, and it keeps the client honest about where the data lives.

### Polling, not push

The dashboard refreshes on a fixed interval rather than holding a socket
open. This is a deliberate v0.2 choice: it needs no backend changes, no
connection lifecycle handling, and no reconnect logic, and a five second
delay is invisible to an analyst reading a screen.

WebSocket or SSE push is a v0.3 item, worth doing when event volume or
alert-to-response time demands it and not before.

## Components

### Backend

#### app.py

The REST API. Ingests events, retrieves alerts, manages policy and exposes
statistics.

Also owns orchestration: `_rescan_actor` loads an actor's history, runs the
detection engine and writes the resulting alerts back. `_rescan_all` does the
same for every known actor.

#### db.py

All SQLite interaction. No other module imports `sqlite3`.

Three tables:

- `events`, raw ingested activity, one row per event
- `alerts`, detector output, one row per fired alert, referencing an event
- `policy`, a single-row table holding the current policy as JSON

Also provides alert querying, severity counts and actor risk scoring. Risk
score is a weighted sum of an actor's alerts: critical 10, high 5, medium 2,
low 1.

#### detectors.py

The detection engine. One pass over an actor's ordered events, maintaining
window state locally, emitting alerts as rules are violated.

Current categories: `allowlist_violation`, `canary_triggered`,
`blocked_target_access`, `dormant_reappearance`, `capability_resurrection`,
`brute_force_auth`, `impossible_travel`, `privilege_escalation`,
`lateral_movement`, `off_hours_access`, `exfiltration_volume`,
`rate_anomaly`.

Severity levels are `critical`, `high`, `medium` and `low`.

#### seed_data.py

Bundled sample events and the default policy, used during development and by
the integration tests. Loaded automatically on first startup and by `/reset`.

#### test_api.py

Integration tests that verify the API behaves correctly after changes. Runs
against an isolated database file.

Currently uses a hand-rolled `check()` runner invoked with
`python test_api.py`, not pytest.

### Frontend

#### src/api.js

The only file that calls `fetch`. Every backend interaction is a thin wrapper
here, which is what makes the dashboard-talks-only-to-the-API rule
enforceable by reading one file.

Reads `VITE_API_BASE`, defaulting to `http://127.0.0.1:8000`.

#### src/App.jsx

Top-level state, the poll loop, and all wiring. Owns filter state, the
selected actor, and whether the policy editor is open.

`POLL_INTERVAL_MS` lives here.

#### src/constants.js

Severity list, actor type list, severity colours and sort order. Shared by
every component that renders an alert, so severity presentation is defined
once.

#### src/components/TopBar.jsx

Branding, connection status and the severity count summary. The connection
dot reflects whether the last poll succeeded.

#### src/components/Sidebar.jsx

Severity, actor type and free-text filters, the list of categories currently
present, and the button that opens the policy editor.

#### src/components/AlertTable.jsx

The alert table. Sorting is client-side over whatever the API returned;
filtering is not. Clicking a row selects that actor.

#### src/components/ActorDrawer.jsx

The full event timeline for one actor, with alerts attached to the events
that produced them, plus a risk composition bar.

#### src/components/PolicyEditor.jsx

Raw JSON editing of the live policy. Saving calls `PUT /policy`, which
rebuilds every alert in the database.

#### src/styles.css

All styling. CSS custom properties at the top define the palette, including
the severity colours that `constants.js` refers to by variable name.

## Data Flow

### On event ingestion

1. Event received at `POST /events`
2. Event stored in SQLite
3. Full event history loaded for each affected actor
4. Detection engine evaluates that history against the active policy
5. Existing alerts for the actor are deleted and replaced with the new set
6. Dashboard picks up the change on its next poll

### On policy change

1. New policy received at `PUT /policy`
2. Policy row updated
3. Every known actor is rescanned via steps 3 to 5 above

A policy change therefore rebuilds the entire alert table. Alerts that no
longer fire under the new policy disappear.

### On dashboard refresh

1. Timer fires, or filter state changes
2. `/stats` and `/alerts` requested in parallel, with current filters as
   query parameters
3. Success updates the table and marks the connection live
4. Failure marks the connection down and shows the error banner, leaving the
   last successful data on screen

## Known Constraints

These are accepted limitations of the current design, recorded so they are
not rediscovered as bugs.

### Alert identity is not stable

Alert rows use an autoincrement primary key and are deleted and reinserted on
every rescan. An alert's `id` therefore changes whenever its actor receives a
new event.

This is now load-bearing for the dashboard. `AlertTable` and `ActorDrawer`
both use `alert.id` as a React key, so rows are torn down and rebuilt on
every poll rather than updated in place.

More importantly, any per-alert state an analyst creates, acknowledgement,
assignment or triage notes, cannot be keyed on `alerts.id` and would be
destroyed by the next ingestion for that actor. Adding analyst state requires
a stable alert identity first, for example a deterministic hash of actor,
event, category and message.

### Rescan cost grows with actor history

Each rescan replays an actor's complete event history. This is acceptable at
development scale but is linear in history length, and a policy change is
linear in total events across all actors.

### No authentication anywhere

Every endpoint is unauthenticated and CORS is open to all origins. The
dashboard has no login. Both are v0.3 items, and the API is intended for
local development only until then.

### Single-writer database

SQLite with the default configuration. Concurrent writers are not supported.
PostgreSQL is planned for v1.0.

### Category filtering is not wired to the UI

`/alerts` accepts a `category` parameter and `db.query_alerts` implements it,
but the sidebar only displays the categories present rather than offering
them as filters.

### Up to five seconds of alert latency

The consequence of polling. A new alert appears on the next refresh, not
immediately.
